# Vita 生产环境外部配置获取指南

本文按实际依赖顺序说明 Vita 上线前需要从外部平台取得的账号、标识、密钥和服务地址。密钥只应写入部署平台的 Secret/环境变量，不要提交到 Git。

## 0. 开始前准备

准备以下权限：

- Apple Developer 与 App Store Connect 的管理员权限
- Google Play Console、Google Cloud、Firebase 的管理员权限
- 域名 DNS 管理权限
- 服务器或云平台、PostgreSQL、Redis 的管理权限
- SMTP 邮箱服务管理权限
- RevenueCat 项目管理员权限
- GitHub 仓库管理员权限
- OpenAI、Anthropic 或其他实际模型供应商账号

建议先确定三个环境：`dev`、`staging`、`production`。生产标识、数据库、Redis、OAuth 客户端、推送凭据、支付项目和模型密钥必须与 dev 分开。

## 1. Android Application ID 与 iOS Bundle ID

### 1.1 命名

采用反向域名格式，例如：

- Android：`com.example.vita`
- iOS：`com.example.vita`

正式发布后不要修改。先确认该标识未被公司其他应用使用。

### 1.2 Android

1. 登录 Google Play Console。
2. 点击“创建应用”，填写应用名称、默认语言、应用/游戏、免费/付费等信息。
3. 在项目 `app/android/app/build.gradle` 或 `build.gradle.kts` 中把 `applicationId` 设置为正式值。
4. 同时检查 `namespace`，一般与 Application ID 保持一致。
5. 创建正式签名密钥库，并把 keystore 文件、alias、密码保存到公司密码管理器。
6. 不要把 keystore 或密码提交到 Git。
7. 首次上传 AAB 后，在 Play Console 的“应用完整性”页面记录 Google Play App Signing 的 SHA-1、SHA-256 证书指纹；Google OAuth 和 Firebase Android 应用会用到它们。

需要最终记录：Application ID、上传证书 SHA-1/SHA-256、Play App Signing SHA-1/SHA-256。

### 1.3 iOS

1. 登录 Apple Developer 的 Certificates, Identifiers & Profiles。
2. 进入 Identifiers，点击 `+`，选择 App IDs → App。
3. 填写 Description 和 Explicit Bundle ID。
4. 按本项目需要启用 Push Notifications、Sign in with Apple 等 Capability。
5. 在 App Store Connect 创建新 App，并选择刚创建的 Bundle ID。
6. 在 Xcode/Flutter iOS 工程中把 Runner 的 Bundle Identifier 改为正式值。
7. 分别检查 Debug、Profile、Release 配置，避免只有一个构建配置被修改。

需要最终记录：Bundle ID、Apple Team ID、App Store Connect App ID。

参考：[Apple 注册 App ID](https://developer.apple.com/help/account/identifiers/register-an-app-id)。

## 2. PostgreSQL、Redis、正式域名与 HTTPS

### 2.1 PostgreSQL

1. 在云数据库或自建 PostgreSQL 中创建生产实例。
2. 选择与 Backend 部署区相同或最近的区域。
3. 创建独立数据库，例如 `vita_production`。
4. 创建专用低权限用户，只授予该数据库所需权限。
5. 限制网络访问，只允许 Backend 所在私网/固定出口 IP。
6. 开启自动备份、时间点恢复、存储告警和连接数告警。
7. 强制 TLS；取得 CA 证书或平台要求的 SSL 参数。
8. 拼出连接串，并从部署环境执行连接和迁移测试。

需要最终记录：数据库 host、port、database、username、password、SSL mode/CA，以及项目实际要求的数据库环境变量名。

### 2.2 Redis

1. 创建生产 Redis 实例，区域与 Backend 一致。
2. 开启 TLS 和认证。
3. 禁止公网开放；使用私网或 IP 白名单。
4. 根据用途配置合理的内存、淘汰策略和持久化。
5. 从 Backend 部署环境测试 `PING`、读写和过期时间。

需要最终记录：Redis URL、用户名（如有）、密码、TLS 参数。

### 2.3 域名与 HTTPS

1. 规划至少一个 API 域名，例如 `api.example.com`；Admin/Webapp 可分别使用独立子域名。
2. 在 DNS 服务商添加 A/AAAA 或 CNAME，指向负载均衡/托管平台。
3. 在部署平台申请受信任 TLS 证书，或使用 ACME 自动签发。
4. 开启自动续期，并确认 80 跳转到 443。
5. 验证证书域名、证书链和到期告警。
6. 把正式 API URL 写入 Admin、Webapp 和后续 App 的正式构建配置。
7. 在 Backend CORS 白名单中只保留正式前端域名。

## 3. SMTP 与旧授权码撤销

1. 选择事务邮件服务或企业邮箱 SMTP。
2. 完成发信域名验证。
3. 在 DNS 添加服务商提供的 SPF、DKIM；生产环境建议同时配置 DMARC。
4. 创建专用 SMTP/API 凭据，不使用个人邮箱登录密码。
5. 记录 host、port、username、password、TLS 模式和发件人地址。
6. 把凭据写入 Backend Secret，并发送注册/登录验证码测试邮件。
7. 检查垃圾邮件、退信和发送额度。
8. 立即在原邮件服务商控制台撤销此前暴露的旧 SMTP 授权码，再生成新凭据。

注意：仅从当前代码删除旧密码不能让泄露的密码失效，必须在邮件服务商处撤销。

## 4. 清理远程 Git 历史中的旧 SMTP 密码

此操作必须由仓库管理员统一安排，会改写历史并影响所有协作者。

1. 先完成第 3 节的旧凭据撤销。
2. 暂停合并和推送，通知所有协作者维护窗口。
3. 使用 GitHub Secret Scanning 或仓库搜索确定泄露文件、提交和分支范围。
4. 建立仓库镜像备份，并限制访问。
5. 使用 `git filter-repo` 按精确路径或精确秘密文本清理全部引用。
6. 在隔离副本中复查所有分支和标签，确认旧秘密不存在。
7. 由仓库管理员强制更新受影响的分支和标签。
8. 要求协作者重新克隆；不要从旧克隆继续推送，否则可能把旧历史带回远程。
9. 清理 PR 引用、缓存、制品和日志中残留的秘密，并重新运行 Secret Scanning。

参考：[GitHub 清理敏感数据](https://docs.github.com/en/authentication/keeping-your-account-and-data-secure/removing-sensitive-data-from-a-repository)、[GitHub Secret Scanning](https://docs.github.com/en/code-security/concepts/secret-security/secret-scanning)。

## 5. Firebase、APNs、Google OAuth、RevenueCat 与商店商品

### 5.1 Firebase 与 FCM

1. 在 Firebase Console 创建生产项目。
2. 添加 Android 应用，Package Name 必须等于正式 Application ID。
3. 填写 Play App Signing 的 SHA-1/SHA-256。
4. 下载 `google-services.json`，按 Flutter/Android 工程规则放置；不要混用 dev 文件。
5. 添加 iOS 应用，Bundle ID 必须完全一致。
6. 下载 `GoogleService-Info.plist`，加入 Runner target。
7. 使用 FlutterFire CLI 生成/更新生产 Firebase 配置。
8. 在 Google Cloud 为 Backend 创建最小权限服务账号；用部署平台的 Secret 或工作负载身份提供凭据。
9. 用 Android 和 iOS 真机分别获取 FCM token，并从 Backend 发送测试通知。

参考：[Firebase Flutter 设置](https://firebase.google.com/docs/flutter/setup)。

### 5.2 APNs

1. 确认 Apple App ID 已启用 Push Notifications。
2. 在 Apple Developer 的 Keys 中创建 APNs Auth Key。
3. 下载 `.p8` 文件；Apple 只提供一次下载机会。
4. 记录 Key ID 和 Team ID。
5. 在 Firebase 项目设置 → Cloud Messaging → iOS app 中上传 APNs key，并填写 Key ID、Team ID。
6. 在 Xcode Runner target 开启 Push Notifications 和 Background Modes → Remote notifications。
7. 使用生产签名真机验证前台、后台、终止状态通知。

参考：[Firebase Flutter FCM/APNs](https://firebase.google.com/docs/cloud-messaging/flutter/get-started)。

### 5.3 Google OAuth

1. 在生产 Google Cloud 项目配置 OAuth consent screen/Google Auth Platform。
2. 设置应用名称、支持邮箱、正式域名、隐私政策 URL、用户协议 URL。
3. 根据目标创建 Android、iOS、Web OAuth Client。
4. Android 客户端填写正式 Application ID 和 Play App Signing SHA-1。
5. iOS 客户端填写正式 Bundle ID。
6. Web 客户端填写 Backend 实际回调地址和允许来源。
7. 把各平台 Client ID 放入对应配置；Client Secret 只放 Backend Secret。
8. 若仍处于 Testing，添加测试用户；上线前按 Google 要求完成发布/验证。
9. 分别验证 Android、iOS、Web 登录和账号绑定。

参考：[Google 配置 OAuth](https://support.google.com/cloud/answer/15549257?hl=en)。

### 5.4 Apple/Google 商店商品

按代码中的产品映射建立完全一致的 Product ID；发布前不要临时改 ID。

Google Play：

1. 上传至少一个可测试的签名 AAB。
2. 在 Monetize products 中创建订阅与一次性商品。
3. 为订阅创建 base plan/offer，并设置国家、价格和税务信息。
4. 激活商品，加入测试轨道，添加 License testers。

Apple：

1. 在 App Store Connect 完成 Agreements、Tax、Banking。
2. 创建 Subscription Group 和自动续期订阅。
3. 创建金币对应的 Consumable IAP。
4. 配置价格、地区、本地化、审核截图和说明。
5. 使用 Sandbox Tester 和 TestFlight 验证购买、恢复、续期、取消及退款状态。

参考：[Google Play 订阅](https://support.google.com/googleplay/android-developer/answer/140504?hl=en)、[Apple IAP 配置](https://developer.apple.com/help/app-store-connect/configure-in-app-purchase-settings/overview-for-configuring-in-app-purchases)、[Apple 消耗型商品](https://developer.apple.com/help/app-store-connect/manage-in-app-purchases/create-consumable-or-non-consumable-in-app-purchases)。

### 5.5 RevenueCat

1. 创建生产 Project，不要复用 dev Project。
2. 添加 iOS App 和 Android App，填写正式 Bundle ID/Application ID。
3. 按 RevenueCat 指引配置 App Store Connect API Key 与 Google Play Service Account。
4. 导入商店商品。
5. 创建 Entitlements（例如 Pro 权益）。
6. 创建 Offerings/Packages，把月付、年付等商品绑定到对应 Package。
7. 配置 Backend webhook URL 和鉴权秘密。
8. 把 RevenueCat iOS/Android Public SDK Key 放入 App 构建配置；Secret API Key 只放 Backend。
9. 验证购买后 App 权益、Backend webhook、数据库状态三者一致。

参考：[RevenueCat Projects](https://www.revenuecat.com/docs/projects/overview)、[Entitlements](https://production-docs.revenuecat.com/docs/getting-started/entitlements)、[Offerings](https://www.revenuecat.com/docs/offerings/overview)。

## 6. 发布隐私政策和用户协议

1. 准备最新英文版 Privacy Policy 与 Terms of Service。
2. 内容至少覆盖账号数据、聊天与 AI 处理、媒体与语音、支付、推送、第三方处理方、数据保留/删除、未成年人、联系方式和适用法律。
3. 在正式 HTTPS 域名发布两个无需登录即可访问的稳定 URL。
4. 禁止通过 `robots.txt`、鉴权或地区规则阻断 Apple/Google 审核访问。
5. 在 Admin 新建对应版本，填写版本号、英文正文/URL，并指定生效版本。
6. 生效后确认 App 注册页展示最新版本和更新时间；不同意时不可注册或登录。
7. 将两个 URL 同步填入 App Store Connect、Google Play、Google OAuth consent screen 和官网。
8. 用无痕窗口与手机蜂窝网络验证可访问性。

## 7. Admin 配置真实文本、图片、音频模型和备选模型

### 7.1 获取模型凭据

1. 在模型供应商创建生产 Project/Workspace。
2. 完成付费方式、额度和预算告警。
3. 创建专用生产 API Key，不复用个人或 dev Key。
4. 记录供应商类型、Base URL、API Key、准确的 Model ID。
5. 确认账号实际有该模型和对应能力的访问权限。

### 7.2 在 Admin 添加供应商

1. 打开 Admin → AI 伴侣 Agent → 模型服务。
2. 选择 OpenAI-compatible 或 Anthropic。
3. 填写名称、Base URL、API Key，并启用。
4. API Key 为只写字段；更新时留空会保留原密钥。

### 7.3 添加模型与可选的真实测试

1. 填写模型服务、远端 Model ID 和显示名称。
2. 勾选模型实际承担的具体场景，而不是只选“文本/图片/音频”大类。
3. `测试可用性`和`添加`是两个独立按钮；测试操作不会创建模型，添加操作也不会调用模型供应商。
4. 如需检查可用性，先选择场景并点击`测试可用性`；不测试也可以直接点击`添加`。
5. 若测试包含“用户语音识别”，可上传一段包含清晰人声的测试音频（不超过 12 MB）；未上传时只有该场景显示测试失败。
6. Backend 会按每个已选场景真实调用供应商接口，并在当前页面展示逐场景成功/失败及错误信息。
7. 测试结果不会启用、禁用或阻止`添加`按钮，也不会随模型配置写入数据库。
8. 图片测试会真实生成图片，语音合成会真实生成音频，因此会产生供应商费用。
9. 视频场景可配置，但当前没有测试/运行适配器；测试会显示失败，且在适配器完成前不能形成可工作的生产视频链路。
10. 已创建模型的供应商、Model ID 和能力不可修改；需要变化时新增模型。

当前 OpenAI-compatible 调用对应 Chat Completions、Images、Audio Speech、Audio Transcriptions 接口。参考：[OpenAI Chat API](https://developers.openai.com/api/reference/cli/resources/chat)、[OpenAI Audio API](https://developers.openai.com/api/reference/typescript/resources/audio)。

### 7.4 配置默认与备选

1. 打开 Admin → 模型路由。
2. 对每个业务场景选择一个默认模型。
3. 按顺序添加备选模型。
4. 系统会展示已启用、能力类型匹配且添加时选择了该场景的模型；是否通过可选测试不会阻止路由配置或运行。
5. 保存后分别执行角色聊天、Life 规划、主动消息、生活照片、请求照片、语音转写和语音合成验收。

## 8. 生产 Beta 全链路验收

必须使用真实 PostgreSQL、Redis、RevenueCat 和 Android/iOS 真机；不能以 mock 或本地接口代替。

建议顺序：

1. 部署 Backend，执行迁移，检查健康接口和日志。
2. 部署 Admin 与 Webapp，确认正式 API、HTTPS、CORS 和登录。
3. 在 Admin 配置法律文档、模型供应商、经真实测试的模型及路由。
4. 安装 Android 内测包和 iOS TestFlight 包。
5. 验证注册、协议同意、登录、创建角色、逐句聊天、Emoji、Life Engine、图片/音频能力。
6. 验证金币购买与全部消费点，检查幂等、失败退款和账本一致性。
7. 验证 RevenueCat 购买、恢复购买、续订、过期、退款和 webhook 重放。
8. 验证 Android/iOS 推送在前台、后台、杀进程后的行为。
9. 验证数据库备份恢复、Redis 故障、模型默认失败后按顺序切换备选。
10. 检查日志、监控、告警中没有 API Key、Token、聊天正文等不应记录的信息。

最终交付应保存一份生产配置清单，只记录 Secret 名称、负责人、创建时间、轮换时间和保存位置，不在文档中填写真实 Secret 值。
